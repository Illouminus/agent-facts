## 2. Метод

**Совокупность.** Все адреса `payTo` в сети Base (`eip155:8453` / `base`) из обоих каталогов: 2 095 адресов. Единица «продавец» = адрес `payTo`. Если у одного владельца несколько адресов, это несколько продавцов; если платформа принимает за многих на один адрес, это один продавец.

**Классы** (`classify-sellers.py`, разметка по доменам ресурсов):
- *крупный бренд* — хотя бы один ресурс на домене из списка: CoinGecko, QuickNode, Exa, Nansen, Glassnode, Chainlink, Pocket Network, Apify, Bitrefill, Alchemy, Messari, Browserbase, Tavily, CoinMarketCap, Zerion, 0x, Blockchain.com, Heurist; Cloudflare, Coinbase и Stripe в списке тоже есть, но ресурсов на их доменах с оплатой на Base в каталогах нет. Итого 26 адресов;
- *платформа* — перепродавцы чужих API и инфраструктура x402: семейство `stable*.dev` Merit Systems, x402scan, Locus, Sponge, PayAI. Итого 30 адресов;
- *мелкий независимый* — все остальные: 2 039 адресов. Случайная подвыборка из 25 с seed 402 нужна для таблицы с описаниями; медиана считается по всем.

**Что считается платежом x402.** Входящий `Transfer` USDC на адрес продавца, после которого в той же транзакции есть событие `AuthorizationUsed` с подписантом-плательщиком. Иначе говоря, перевод исполнен через EIP-3009 `transferWithAuthorization`: это способ по умолчанию в схеме `exact` x402 для USDC (`docs/schemes/exact.mdx` в репозитории). Формат сверен на живой транзакции `0xd2b5681c…b8f5` (`data/probes.json`): вызов `0xe3ee160e` (`transferWithAuthorization`) с адреса `0x14fd…` на контракт USDC, в логах события 2: `AuthorizationUsed` и `Transfer`. Все входящие USDC без этого условия тоже посчитаны (`all_in_*` в CSV).

**Фильтры шума** («чужой» плательщик = плательщик x402 минус отсеянные):
1. *самоплатёж* — плательщик совпадает с продавцом;
2. *пополнен продавцом* — продавец в окне сам переводил USDC этому адресу (фондирование своих кошельков или круговой платёж). Для этого скачаны все исходящие USDC всех 2 095 продавцов;
3. *тот же владелец* — плательщик сам является `payTo` другого продавца с тем же основным доменом;
4. *обходчик / лидерборд* — плательщик за окно платил ≥ 20 разным продавцам каталога. Это кошельки, которые проходят каталог по 1–2 платежа на продавца. Например, `0xa1d1…1978` заплатил 1 274 продавцам (1 798 платежей), nonce 0, код 0 байт; `0xc9c7…1670` заплатил 1 082 продавцам (5 216 платежей), nonce 0, код 0 байт; `0x6a0b…4518` заплатил 906 продавцам (8 522 платежа), nonce 0, код 0 байт. Nonce 0 значит, что кошелёк сам не отправил ни одной транзакции: он только подписывает платежи, а газ платит фасилитатор (`data/probes.json`). Чувствительность к порогу — в разделе 7;
5. *сибилы* — плательщики одного продавца, у которых первое пополнение USDC в окне пришло с одного адреса F, склеиваются в один «кластер». Условие: таких плательщиков ≥ 3 и либо ≥ 80 % всех чужих плательщиков, пополненных F, платят именно этому продавцу (F существует ради него), либо ≥ 50 % платят ему и больше половины пополнений — одна и та же сумма (раздача, а не вывод с биржи). Пополнения скачаны для всех плательщиков x402, кроме обходчиков (порог 20) и самих продавцов. Порог концентрации защищает от ложной склейки клиентов биржи или DEX-роутера: они пополняют плательщиков самых разных продавцов. Например, роутер 1inch (`0x1111…`) в данных пополнял плательщиков Nansen, Otto AI и других и не склеен.

**Основная метрика**: *уникальные чужие кластеры за 30 дней*. Дополнительно в CSV: *повторные чужие плательщики* (платили в ≥ 2 разных сутках), *активные дни*, *доля платежей в самом плотном часе* (тестовые всплески), *чужие поступления в $*.

## 8. Выводы

1. **Базовая ставка — около одного чужого плательщика в месяц.** Медиана чужих кластеров у мелкого продавца — 1, у 44.4 % нет ни одного, p75 = 1, p90 = 4. Если считать обходчиком кошелёк, платящий ≥ 5 продавцам, медиана падает до 0. Плательщик, вернувшийся во вторые сутки, есть только у 30.5 % мелких; медиана повторных — 0.
2. **Денег почти нет, и они сосредоточены у единиц.** Медиана чужих поступлений мелкого продавца — $0.0099 за 30 дней, p90 — $2.40. Все 2 039 мелких вместе получили $24 421.95, из них 83.2 % пришлось на десять получателей. Чужие поступления ≥ $100 у 18 мелких.
3. **«Уникальные плательщики» в дашбордах раздуты обходчиками.** Без фильтров медиана — 4 плательщика x402, после фильтров — 1. 133 кошелька, плативших ≥ 20 продавцам, сделали 132 987 платежей (11.1 % всех x402-платежей продавцам каталога на Base) на $1 834.19. Самый широкий заплатил 1 274 продавцам. Такие кошельки дают «плательщика» почти любому продавцу из каталога.
4. **Сибилы есть и у лидеров.** У ax1.vc 3 622 чужих плательщика, но 2 529 из них пополнил один адрес (EOA, nonce 11 511); после склейки остаётся 465 кластеров. У onesource.io 1 217 → 152: 1 035 плательщиков пополнил один адрес (EOA с делегированием EIP-7702, nonce 6 619), и все они платят только этому продавцу. Отдельно есть ферма: адрес `0x6ab0…` пополнил 31 кошелёк, каждый из них платит 16–19 продавцам (96 продавцов всего). Это обходчик, разрезанный под порог; склейка ловит его только частично.
5. **Крупные бренды на порядок-два выше медианы, но в абсолюте тоже немного.** CoinGecko — 35 кластеров, 6 повторных, $2.09; Nansen — 175 кластеров, 56 повторных, $97.12; Glassnode — 35 кластеров, 20 повторных, $58.22; Exa — 138 кластеров, 37 повторных, $22.50; Bitrefill — 99 кластеров, 12 повторных, $9 569.13; Pocket Network — 36 кластеров, 62 повторных, $141.31; Apify — 25 кластеров, 10 повторных, $516.00. Даже у лидеров среди брендов (Nansen, Exa) на Base за месяц порядка одной-двух сотен чужих плательщиков, а не тысячи. Оговорка: у части брендов адрес из каталога пуст (см. п. 8 раздела 9).
6. **Заметный спрос — у 5.1 % мелких.** Чужих кластеров ≥ 10 у 105 мелких из 2 039 (5.1 %), ≥ 5 повторных чужих плательщиков у 50. Наверху ИИ-шлюзы (BlockRun) и крипто- и финансовые данные (Otto AI, hugen.tokyo, onesource.io), см. раздел 5; у части лидеров заметная доля плательщиков — сибилы (п. 4).
7. **Весь «пирог» каталога на Base за 30 дней**: 9 759 уникальных плательщиков x402 и $50 276.07 на 2 095 адресов продавцов, включая обходчиков и сибилов. За него конкурирует любой новый продавец.
8. **Для решения о втором шаге.** Новый мелкий эндпоинт без собственного трафика, по данным, может рассчитывать на 0–1 чужого плательщика и центы в месяц. Это не противоречит тезису брифа, что заметная доля активности x402 — тесты и накрутка. Сам этот тезис замер не перепроверял. Пробный эндпоинт имеет смысл ставить только как замер, где порог успеха заранее выше p90 мелких: больше 4 чужих кластеров и хотя бы один повторный плательщик за 30 дней. Иначе результат неотличим от фонового шума обходчиков.

## 9. Что не удалось отфильтровать или измерить

1. **Агент или не агент — по блокчейну не различить.** «Чужой плательщик» — это любой независимый от продавца адрес: автономный агент, скрипт разработчика, человек с кошельком через UI-клиента или тестовый прогон чужой команды. Отсеиваются только явные формы шума. Поэтому найденное число — верхняя граница спроса *автономных агентов*, а не оценка.
2. **Сибилы, пополненные вне окна или через посредников.** Пополнитель ищется только среди переводов USDC на Base за те же 30 дней; найден для 7 437 из 8 940 чужих плательщиков. Ферма кошельков, пополненная раньше окна, через биржу (горячий кошелёк биржи выглядит как независимый источник), через мост, своп или в несколько прыжков, фильтром не ловится.
3. **Вторые кошельки владельца, которых нет в каталоге.** Если продавец платит сам себе с кошелька, который не указан в каталоге и не получал от него USDC в окне, это засчитается как чужой плательщик.
4. **Порог «обходчика» условный.** Кошелёк, который честно пользуется 20+ сервисами в месяц, отсеивается вместе с обходчиками. В обратную сторону, обходчик, прошедший 19 продавцов, остаётся. Чувствительность показана в разделе 7: медиана чужих кластеров при порогах 5, 10, 50, 100 равна 0, 1, 1, 1, без фильтра обходчиков (сырые плательщики x402) — 4.
5. **Платежи x402 не через EIP-3009.** В каталогах из 57 364 предложений на Base: `permit2` — 1 116, схема `upto` (тоже Permit2) — 799, `batch-settlement` — 136 (`data/catalog-stats.json`). Такие платежи попадают только во «все входящие USDC» (`all_in_*`), а не в метрику x402. Платежи в других токенах на Base (1 209 предложений с активом не USDC) и **все сети, кроме Base**, не измерялись. Только в каталоге CDP предложений на Solana 9 705, на Polygon 5 744. Агент, который платит этому же продавцу на Solana, здесь не виден.
6. **Продавцы вне двух открытых каталогов** не видны: без расширения bazaar, на других фасилитаторах, со Stripe без bazaar. Есть и эффект отбора внутри каталога: по спецификации (`specs/extensions/bazaar.md`) фасилитатор каталогизирует ресурс, когда обрабатывает по нему платёжную подпись (verify/settle). Значит, почти у каждого продавца в каталоге был хотя бы один платёж или попытка, возможно его собственный тестовый.
7. **Классификация «мелкий / бренд / платформа» по доменам — ручная эвристика.** Среди «мелких» есть стартапы с финансированием и агрегаторы (в топе раздела 5, например BlockRun, AX1). Наоборот, на домене бренда может сидеть сторонний посредник. Семейство `stable*.dev` записано в платформы частично по шаблону имени.
8. **Ротация `payTo`.** В каталоге лежит один снимок адреса. Если продавец выдаёт новый адрес на каждый запрос (так можно делать с депозитными адресами Stripe), платежи на другие адреса здесь не видны. Признак — каталог CDP приписывает ресурсу плательщиков за 30 дней, а на адрес из каталога в окне не пришло ни одного USDC. Таких адресов 64 из 2 095: среди крупных брендов 9 (это адреса брендов Browserbase, Tavily), среди мелких 55. Часть из них может объясняться и платежами в другой сети: метрика каталога, похоже, общая для всех сетей ресурса. Для них ноль на Base — нижняя граница, а не измерение.
9. **Метрика каталога `quality.l30DaysUniquePayers`** приведена только для сверки: как она считается (с обходчиками или без, по каким сетям), не документировано.
10. **Не измерено**: что получил плательщик (ответ, ошибку, возврат вне сети), реальная цена против заявленной, выручка в фиатном эквиваленте сверх номинала USDC, а также динамика за пределами этих 30 дней. Тезисы из брифа («−93 % к пику Q4 2025», «25–30 % накрутки») этим замером не перепроверялись: снята история только за одно окно.

## 10. Проверка целостности ([`data/verify.txt`](x402-demand/data/verify.txt))

- Все 8 наборов логов (`in`, `out`, `auth`, `in2`, `out2`, `auth2`, `fund`, `fund2`) покрывают окно по 260 чанков, без дыр между чанками.
- Два продавца из случайной выборки пересчитаны независимым скриптом `verify-refetch.mjs`: прямые запросы к другому RPC, диапазонами по 50 000 блоков, мимо сборщика и сырых выгрузок. Число входящих переводов, отправителей и сумма совпали с `seller-metrics.csv` до последнего знака.
- В `seller-metrics.csv` для всех 2 095 адресов выполняется кластеры ≤ чужие ≤ плательщики x402 ≤ все отправители USDC, а плательщики x402 = чужие + сумма отсевов.

## 11. Как воспроизвести

```bash
cd ~/dev/app-market-research/x402-demand
node fetch-catalog.mjs && node fetch-catalog.mjs payai        # каталоги -> raw/catalog*/, data/catalog*-items.jsonl
python3 -I classify-sellers.py                                # data/sellers.csv, data/sample-small.json
node fetch-logs.mjs window                                    # фиксирует окно (data/window.json); при повторе окно сдвинется
node fetch-logs.mjs in data/payto-base.json && node fetch-logs.mjs out data/payto-base.json && node fetch-logs.mjs auth
node fetch-logs.mjs in2 data/payto-base-payai-only.json && node fetch-logs.mjs out2 data/payto-base-payai-only.json && node fetch-logs.mjs auth in2
X402_MAX_TOPICS=10000 node fetch-logs.mjs fund data/fund-addrs-1.json   # (+ fund2 для плательщиков продавцов PayAI)
python3 -I compute-demand.py && for n in 5 10 50 100; do python3 -I compute-demand.py --crawler $n; done
python3 -I catalog-stats.py && node probes.mjs && python3 -I make-report.py
node verify-refetch.mjs                                       # независимая сверка двух продавцов (~10 мин)
```

Сырые выгрузки: `raw/catalog*/page-*.json.gz` — ответы каталогов как есть; `raw/logs/{in,in2,out,out2,auth,auth2,fund,fund2}/<блок>.json.gz` — логи `eth_getLogs` чанками по 5 000 блоков. Из каждого лога сохранены блок, номер транзакции в блоке, номер лога, хеш транзакции, `topics` и `data`; поле `rpc` показывает, какой провайдер отдал чанк. Производные таблицы: `data/sellers.csv`, `data/seller-metrics*.csv`, `data/payers*.csv`, `data/summary*.json`.
